   - mark7/8/9 的 CMake 仍然依赖 `libpcap`，源码仍是 PCAP replay。
   - 没有发现真正的 DPDK RX/mbuf/EAL 在线路径。
   - 周报中的“在线原型”更准确地理解为 PCAP replay 的在线式 flow state 和调度流程，而不是已验证的真实网卡系统。

6. **真正的算法薄弱点已经被找出来，但还没有实现。**
   - 当前 `W_i = added_cost - retired_cost` 并不是真正的剩余检测工作。
   - 预计代价在首包时一次性加入，首包被消费后就 retire；一个已经处理了大部分包、但尚未完成识别的流，可能不再计入 backlog。
   - 因此目前更准确的说法是“基于预计代价的 flow-level admission heuristic”，不能直接宣称是严格的 residual-work JSW。
   - `progress-aware residual work`、`runnable/latent backlog`、`uncertainty-aware dispatch` 目前还是后续算法方向。

**IWQoS 版本建议怎么讲**

当前最稳妥的主线不是把 DPU 或多机集群硬塞进来，而是：

> **Adaptive QoS-aware Scheduling for Stateful Software DPI on Heterogeneous Multicore Servers**

中文可以理解为：

> 面向异构多核服务器上有状态软件 DPI 的闭环代价感知 QoS 调度。

论文核心问题是：

> nDPI 流在首包到达时，最终协议和完整检测代价都未知；但此时必须将流绑定到某个 P/E worker，且后续不能迁移。如何利用首包 prior、当前异构核负载和在线反馈，在流量分布变化时控制 time-to-classification 的尾延迟？

论文内容大致分为五部分：

1. **Measurement：证明这个问题值得做**
   - 不同协议的检测代价差异很大，目标是复测并确认约 18 倍量级。
   - P/E 核之间存在稳定的能力差异，目标是验证约 1.8 倍的 speed ratio。
   - 同一协议的绝对检测代价会随流量模式发生漂移，说明静态代价表不够。
   - 检测代价应定义为“从流开始到 nDPI 完成协议识别期间的累计检测 CPU 代价”。

2. **Offline Prior：构建首包代价先验**
   - 离线 profiling 得到 `protocol -> cost`。
   - 再通过端口、payload prefix 等首包特征构建轻量规则表。
   - 规则表输出 `proto_hint` 或 cost prior，而不是假设首包就能准确识别最终协议。
   - 低置信度流回退到静态 bucket 或保守代价。

3. **Online Dispatch：异构核上的流分派**
   - 对每个 worker 维护容量归一化的 pending/residual work。
   - 理想形式是：
     \[
     i^*=\arg\min_i\left(L_i+\frac{\hat p_f}{s_i}\right)
     \]
   - `L_i` 表示 worker 当前工作量，`s_i` 表示 P/E 核能力，`\hat p_f` 是首包预测的检测代价。
   - 流首次分配后保持严格 flow affinity。

4. **Closed-Loop Adaptation：在线修正**
   - worker 在协议识别完成后记录 `(protocol_id, actual_cost, core_type)`。
   - dispatcher 通过 feedback ring 收集实际代价。
   - EWMA 更新协议代价和 P/E 能力标定。
   - 流量发生 distribution shift 时，提高学习速率或触发 fallback。
   - 这一部分必须和“隐藏、逐步揭示的检测工作”绑定，否则容易被审稿人评价为“EWMA + JSW 的工程组合”。

5. **QoS Evaluation：用 QoS 证据而不是只报吞吐**
   - 主指标建议改为 `time-to-classification` 的 p95/p99 或 SLO violation rate。
   - 同时报告吞吐、丢包、backpressure、每核 residual-work imbalance、适应时间和调度开销。
   - 关键场景包括：
     - 稳态混合流量；
     - 流量分布突变；
     - 人为注入错误 prior；
     - microburst 和高负载；
     - P/E 异构 worker；
     - 冷启动收敛；
     - overload graceful degradation。

建议至少对比：

- RSS/hash；
- JSQ；
- 静态 cost-aware；
- mark8/mark9 adaptive cost-aware；
- Oracle/clairvoyant reference。

**论文真正需要强化的地方**

目前最危险的版本是：

> 离线表 → weighted JSW → EWMA 更新。

这套内容有工程价值，但算法新颖性偏弱。IWQoS 版本最好把核心科学对象改成：

> **在严格 flow affinity 下，对“隐藏且随数据包逐步揭示”的检测工作进行 QoS-aware residual-work 估计和闭环调度。**

也就是说，后续最好优先解决：

- dispatcher 如何低开销观察 worker 上的流处理进度；
- 如何区分 runnable backlog 和 latent backlog；
- 如何处理错误 prior、重尾流和流量漂移；
- 如何证明预测误差或 EWMA 跟踪误差会怎样影响尾延迟；
- 如何在预测失效时保证性能不会显著差于 JSQ/RSS。

DPU/多机方向目前更适合作为扩展或下一篇论文。除非能证明 DPU 表容量、规则更新时间、状态一致性和延迟反馈形成了新的联合决策问题，否则“CPU 做检测、DPU 做转发”本身更像已有工程模式。

一句话总结：

> **当前已经有一条可运行的 mark7 实验基础和 mark8/mark9 的闭环升级代码，论文方向也从普通异构 DPI 调度升级为面向 TTC 尾延迟的闭环 adaptive flow dispatch；但距离可投稿 IWQoS，最关键的缺口仍是 mark8+mark9 合并验证、规范实验、DPDK/在线路径取舍，以及把 residual-work/hidden-cost 机制做实，避免论文停留在“EWMA 加权 JSW”。**
